# INKR V5 — audit de reprise

12 novembre 2026. Base : `main` à `5c995e1`, refonte Claude `9d98ff4` (111 fichiers modifiés). Branche de travail : `codex/inkr-v5-completion-excellence`.

## Niveau de preuve

Le dépôt contient 48 écrans routés hors layouts et `+html`. Les 125 tests préexistants passaient avant intervention. La baseline TypeScript échouait dans `lib/auth-errors.ts` (deux paramètres implicitement `any`). ESLint passait avec trois avertissements dans `TToast`. L'export web échouait sans `EXPO_PUBLIC_SUPABASE_URL`, ce qui est attendu dans cet environnement sans variables de projet. Avec une URL et une clé **fictives**, l'export a réussi. Ce build ne valide aucune requête vers la vraie base.

Une session Chromium locale a rendu `/explore` à 360, 390, 768, 1024 et 1440 px : pas de débordement horizontal ni d'erreur JavaScript. L'état erreur réseau s'affiche, car la configuration est fictive. Les captures sont dans `/workspace/shared/inkr-explore-*.png` (hors dépôt). Aucun backend **de test**, compte de test ni appareil iOS/Android n'est disponible ici. Les états et permissions non observés en condition réelle portent donc la mention **NV**.

Inspection **en lecture seule** du projet Supabase connecté `inkr` : il est actif et expose les tables principales du produit, mais son historique contient neuf migrations (`001` à `009`) aux noms différents de ceux du dépôt (`001_initial` à `012_booking_care`). `search_artists` y existe, `artist_portfolio_previews` n'y existe pas. Le bucket `request-references` est privé et limité à 10 Mio, mais `allowed_mime_types` vaut `NULL`, contrairement à la migration locale. L'écart exige une réconciliation de schéma avant tout déploiement ; aucune requête d'écriture n'a été envoyée à ce projet. Les conseillers de sécurité Supabase signalent aussi des fonctions à `search_path` mutable et des fonctions `SECURITY DEFINER` exécutables par `anon` ; leur caractère intentionnel reste à examiner ([guide Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)).

Une seconde exportation locale avec la clé **publiable** du projet actif a permis de tester uniquement les lectures publiques : `/explore` a affiché un artiste réel ; la navigation vers son profil a affiché son nom, ses spécialités, son statut et « Demander un projet » dans la première hauteur à 390 px, sans débordement ; le bouton a ouvert `/sign-in` avec un paramètre `next` pointant vers le brief de cet artiste. Le profil a aussi été capturé à 1440 px (`/workspace/shared/inkr-live-artist-*.png`). Le RPC d'aperçus répond 404 tant que la migration n'est pas déployée ; la carte reste affichée grâce au repli. Une ouverture directe du profil a produit une erreur React d'hydratation `#418` en console avant de se rendre normalement : défaut de rendu à diagnostiquer. La base publique ne contient qu'un artiste visible au moment du test ; elle ne peut pas prouver l'équilibrage multiartiste.

Le 13 novembre, une nouvelle exportation avec la même clé publique a vérifié `/explore` et l'ouverture directe du profil à 390, 1024 et 1440 px. Les six chargements n'ont montré ni débordement horizontal ni erreur React en console. Le clic « Demander un projet » depuis le profil conduit à `/sign-in` avec le retour exact `/request/new?artistId=…`. L'erreur d'hydratation #418 antérieure n'est donc pas reproduite sur cette version, sans preuve suffisante pour la déclarer définitivement corrigée. Les captures locales `inkr-qa-explore-reordered-*` et `inkr-qa-artist-*` sont dans `/workspace/shared` (hors dépôt). La liste d'artistes passe désormais avant les rails de découverte ; le résultat est visible dans le premier écran sur téléphone.

Les exports Hermes Android et iOS réussissent avec une configuration Supabase fictive. Ce contrôle valide le bundling des deux plateformes, mais aucun parcours n'a encore été exécuté sur un appareil ou un simulateur natif.

Après autorisation Vercel le 13 novembre, les deux journaux de build de `9b65c1c` ont révélé les causes exactes : le projet `tattoo-app` échouait sur `supabaseUrl is required` car il n'avait aucune variable Supabase ; `tattoo-app-4gmu` échouait sur `supabaseKey is required` car sa clé publique était ciblée sur Production seulement. Les variables manquantes ont été ajoutées **uniquement à Preview**, en utilisant la même URL et clé anonyme publiques déjà présentes dans la configuration Vercel ; aucun secret n'a été ajouté au dépôt et aucune variable Production n'a été modifiée. Les deux previews et la CI ont ensuite réussi sur `d690e80` ; `/explore` et le profil public ont répondu HTTP 200 sur les deux déploiements. Leurs variables Preview ont été changées le 13 novembre pour viser le projet de test isolé `lsewxsdulunuuzmszegm`, avec une URL spécifique à cette branche sur `tattoo-app-4gmu` pour préserver sa variable Production. Les deux bundles de `53178ab` ont été lus via Vercel : ils contiennent l'URL du projet de test, aucune occurrence de celle du projet actif, et `/explore` répond 200. Les quatre checks de `b8ada11` sont verts.

Sur ce projet de test, les quatorze migrations du dépôt ont été appliquées dans l'ordre et le bucket `request-references` est privé, limité à JPEG et à 10 Mio. Quatre comptes Auth fictifs ont été créés via Auth Admin dans une fonction temporaire restreinte au projet de test, puis cette fonction a été rendue inerte (HTTP 410). Les essais HTTP à trois identités ont confirmé les lectures client et artiste, le refus du tiers, trois emplacements, la taille et le MIME, le remplacement, l'expiration courte, la suppression, la reprise et la table historique. Storage peut répondre avec succès et zéro fichier supprimé à une suppression non autorisée : le client vérifie donc l'identité du propriétaire avant l'appel, puis la disparition de l'objet avant d'effacer sa ligne historique. Un lien signé déjà chargé reste toutefois lisible depuis le cache après suppression ; sa durée a été réduite à une minute, avec renouvellement automatique et information après suppression. Le cycle dans l'interface web est décrit ci-dessous.

## Légende de couverture

- **P** : parcours ou composant V5 présent dans le code ; **V** : rendu visuellement vérifié ; **NV** : non vérifié en interaction réelle.
- **E** : état erreur explicitement constaté ; **C** : état de chargement ou vide repéré dans le code ; **?** : état non encore audité.
- **PARTIAL** : un écart concret reste ouvert ; **NOT VERIFIED** : aucun défaut affirmé, mais la définition de terminé n'est pas prouvée. Aucune route n'est déclarée COMPLETE sur la seule base d'un build.

## Écarts classés

1. **P1 — Références du brief** : sélection de trois images, compression JPEG, plafond 10 Mio, stockage sous l'identifiant de la demande et lecture signée depuis le bucket privé implémentés. Un échec après création conserve l'identifiant en session ; un marqueur local contenant uniquement cet identifiant permet de retrouver le dossier après réouverture et de réutiliser le même identifiant après une réponse réseau ambiguë. Si cette vérification échoue, le formulaire attend une nouvelle vérification au lieu de permettre un envoi potentiellement trompeur. Un ancien identifiant ne peut pas faire passer un brief différent pour une nouvelle demande. Le dossier liste les fichiers déposés et permet au client d'en ajouter ou retirer ; les URI d'images ne sont pas conservées localement, donc elles doivent être resélectionnées après fermeture. Le chemin privé est enregistré de façon idempotente dans `request_references` ; le bucket reste la source de vérité pour l'affichage. La migration locale, **non appliquée au projet actif**, ajoute l'unicité des chemins, les droits de suppression du client, limite les noms à trois emplacements et impose JPEG et 10 Mio côté Storage. Elle a été appliquée et testée sur `inkr-v5-staging`. Les liens signés expirent après une minute et sont renouvelés toutes les 45 secondes pendant l'ouverture du dossier ainsi qu'au retour au premier plan. L'API réelle à trois identités et l'expiration ont été testées ; le cache peut encore servir un lien déjà utilisé jusqu'à son expiration. L'ajout, la lecture, la suppression et la nouvelle tentative dans l'interface web ont été vérifiés ; les appareils natifs restent à tester.
2. **P1 — Validation des écritures** : le compte et la fin d'onboarding annonçaient un succès avant la réponse serveur. Corrigé dans cette branche ; validation avec un backend de test encore requise.
3. **P1 — Aperçus recherche** : une limite globale pouvait masquer le portfolio des derniers artistes d'une page. Un RPC à quota par artiste, avec index et test SQL, est préparé. La migration doit précéder le client.
4. **P2 — Studio** : les chiffres précédaient les demandes à traiter. Ordre et hauteur de titre ajustés ; validation avec un compte artiste chargé encore requise.
5. **P2 — Actions factices** : lien App Store `id000000000` et commande photo ouvrant seulement une alerte retirés. Il reste à concevoir une vraie modification de photo.
6. **P1 — Écart de schéma connecté** : l'historique du projet actif et le dépôt ne concordent pas. Ne pas appliquer aveuglément les migrations du dépôt au projet actif.
7. **P2 — Hydratation du profil** : ouverture directe d'un profil réel : erreur React `#418` puis rendu normal. Vérifier la différence entre HTML statique et état client avant publication.
8. **P1 — Conversation** : l'envoi texte utilise maintenant un identifiant de message stable. Une réponse perdue est vérifiée par cet identifiant avant d'afficher un échec ; un message non confirmé reste visible et relançable avec le même identifiant. Les caches privés sont vidés au changement de compte. L'ancien bouton d'image de conversation utilisait `posts-media/conv/<demande>/…`, refusé par la policy Storage active `inkr_posts_media_insert_own_artist` pour le client comme pour l'artiste. Il a été retiré ; les références du projet restent gérées dans le dossier privé. Des pièces jointes de conversation exigeraient un bucket privé distinct et ses tests HTTP sur l'environnement isolé.
9. **P1 — URL directe de conversation** : corrigée après reproduction avec le compte tiers. L'accès au dossier est confirmé avant de récupérer les messages, de s'abonner à Realtime ou d'afficher le composeur. Test réel à trois identités effectué sur le staging.
10. **P1 — Paiement de test** : le pont HTTPS de retour natif manquait au code actif ; il est intégré et testé sur le staging. Le Checkout s'arrête désormais avec `checkout_unavailable` si la clé ou le prix Stripe manque. La recette du paiement, de la signature webhook et du changement d'abonnement attend une configuration `sk_test_…`, deux prix de test et le secret webhook sur le projet isolé. Les origines des previews doivent aussi être autorisées via `ALLOWED_ORIGINS`. Ne pas reprendre les secrets du projet actif.
11. **P1 — Images web** : la CSP empêchait la lecture des URL `blob:` produites par le sélecteur. L'autorisation `blob:` a été ajoutée à `connect-src` sans élargir les domaines distants. Le cycle réel de référence privée client/artiste/tiers, retrait et nouvel envoi passe sur le staging.
12. **P1 — Publication directe** : une publication réussie depuis `/create` ouvert directement conservait le formulaire, ce qui permettait un second envoi accidentel. La navigation remplace maintenant l'écran par le Studio après la confirmation serveur ; la recette réelle a validé la redirection et l'apparition du post public.
13. **P2 — Garde artiste au chargement** : les écrans de création montraient un refus avant que le profil soit restauré. Un squelette commun évite ce faux état, avec refus réel conservé pour un compte client.

## Validation restante avant de qualifier la V5 de complète

Parcours client et artiste avec comptes de test, stockage privé avec un tiers non autorisé, paiements Stripe en mode test, alertes, états de données vides et chargées, zoom 200 %, clavier, VoiceOver/TalkBack, appareils natifs, performance mesurée et essais avec tatoueurs. L'absence de ces preuves interdit de déclarer les missions A et B achevées.
